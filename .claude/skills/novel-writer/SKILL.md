# 写作规范

## 资料在哪

- **世界观和规则**：`bible.md`（世界、落星亭、宗门、资质、功法、丹药、符箓、法器、法宝、炼器、炼丹、阵法、御兽、傀儡、紫气、命名规矩、跨线规则）。写着“暂无设定”的类目，正文要用到时先在 `bible.md` 里补设定（新机制先跟用户确认），再写正文。
- **人物、关系、地点、伏笔、剧情线、章节规划**：`story/*.json`，由星图书房（`studio/`）维护。人物“当前状态”是 `characters.json` 里每人的 `progressions`：从第几章起，哪一项变成什么。
- **写到哪了**：`progress.md`。

## 开写前

1. 生成并读写作上下文：
   ```bash
   node studio/scripts/cli.mjs context N
   ```
   输出到 `story/context/chapNN.md`。里面有本章计划和各剧情线任务、前五章实际写了什么、后三章安排（别提前写掉）、相关人物在本章开写时的状态和关系、相关地点（含古今对照）、未收伏笔、已发生的历史改动、必守设定。如果 `studio/node_modules` 不存在，先在 `studio/` 里 `npm install`。
2. 读 `outline.md`：本章及前后两章的安排。
3. 上下文里没覆盖、但本章涉及的设定，去 `bible.md` 或 `story/` 里查。凡是涉及落星亭、境界、地点、紫气，都先查，不凭记忆写。

**一次写多少**：可以一次连写多章，一个阶段甚至一整卷都行，不必每写一两章就停下来等用户看。连写时守住三条：

1. **每一章单独走一遍“开写前”和“写完自检”**，不能因为连写就省掉。每章开写前重新生成这一章的写作上下文，因为前一章写完后，人物状态和伏笔都可能变了。
2. **每章写完立刻同步**（见“写完同步”），至少更新 `progress.md` 和 `story/chapters.json`。下一章的写作上下文靠这些数据给出前情，不同步就会接错。
3. **每写完一个阶段，回头通读这个阶段**：对照 `bible.md` 查设定有没有走样（落星亭规则、境界、古今地名、物价、紫气只写表现），对照 `outline.md` 查剧情有没有偏，跑一遍不带章号的守卫看全书。偏了就先改正文，再往下写。

正文放在 `chapters/chapNN.md`。开头写 `## 第N章：标题`；每卷第一章再加一行 `# 第X卷：卷名`。

## 节奏

- **篇幅**：一章 2600–3200 字，2–3 个场景（`---` 分隔，守卫会数）。每个场景要写够：有进入，有变化，有落点。
- **日常写快**：快是靠跳过时间，不是靠切碎场景。一句话带过三五天（“往后三天，他每夜都去”），然后挑一个最好的场面写满。
- **关键事件写慢**：一件事写 2–3 章，写到准备、现场、代价和善后，不要用一两段转述带过。
- **古今各走各的节奏**：两条线不镜像。不是每章都要有子时戏，也不按今古严格轮换。
- **相邻三章不同构**：“有人刁难 → 主角当众压场 → 众人震动 → 拿到好处”这个套路，每个阶段最多用一次。
- **主角会错**：林凡会判断错、会失手；苏清月也要反过来教林凡。两人都不是万能的。
- **每章至少有一个读者能复述的具体场面**，不能只有剧情摘要。
- **高潮章**：至少写三个视角，其中一个给对立的一方或旁观的人。动作句短，单独成段。情绪到了顶点不要停在那里，接一个低调的细节或一句笑话再收。

## 母题与人物

- **母题**（`bible.md` 1.1）：看见账对不上的人，和学会看不见的人。每个阶段至少有一场戏撞上这个问题，要用事件撞，不要说教。
- **代价**：林凡因为“眼神好”吃的亏，要能算清楚：钱、名次、人情、一夜的话费。苏清月学会看见师尊也会错，付的是师命和名声。
- **反方要体面**：“学会看不见”的人有他的道理（李胖子是穷人的活法，刘大爷的“压着它”真压住了几千年）。不要写成蠢人或坏人。每卷至少有一场争论，让主角说不赢。
- **配角翻面**：重要配角先让读者有一个判断，之后用一整场戏把它翻过来。翻面要有一个私人的理由，而且和主角无关。

## 文风

**基调**
- 轻松搞笑。叙述克制，笑点放在对白、处境和反差里。
- 一场戏只用一个现代梗（“话费”“KPI”之类）。古人用现代词时一本正经，不改成古风说法。

**写法**
- 先写现象，再下结论：先写看见、听见、闻见、摸到的，再让人物判断这意味着什么。不要用“这说明……”代替过程。
- 修炼戏要有身体感，涉及境界时给出参照。阵法戏写灵光、纹路和灵力走向，不要写成修水管。
- **叙述者可以有态度**：每章可以有一两句冷幽默或议论，对准宗门的规矩、配给、手册、外务房这类繁文缛节，比如“灵气要排队，这条规矩倒是一万年没变”。不要对人物的内心下结论，那仍然算感悟。
- **段落**：叙述不要一句一段。“林凡没接话。”“那头静了。”这类短句，并进前后的段落。对白照旧写短。
- 【亭】戏只有声音：每场至少写一种对面的背景音，比如翻书、大白的爪子、风铃的远近、茶盏、她走动。林凡判断她的状态，只能靠耳朵。
- **停顿是稀缺品**：“没说话”“过了很久”“那头没有声音”、单独成段的“嗯。”，每章合计不超过 3 处（守卫会数），只留给有含义的那一次。平时的节拍用对面的动静来打。第 23 章能从“七个嗯”里听出她出事，是因为平时她不这样说话。
- **煽情到顶就打岔**：情绪最满的时候，让一方说句不相干的话把气氛打断，像第 23 章的袜子那样。

**伏笔**
- **读者已经知道的事，不要再提示**：紫气有问题，读者从第 30 章起已经确定了。往后不再加“甜”字式的暗示。新的提示必须带一个能计量的变化，当作倒计时：柳如烟又多穿了一件、离开泉边多久开始发抖、斗篷还没还。
- **物件和口头禅要设计第二次出现**：第一次轻描淡写，第二次在相反的处境里出现，最好由另一个人说出来，情绪要变。比如林凡的“我眼神好，没办法”，可以在苏清月违抗师命时从她嘴里说出来。设计好的登记进 `story/foreshadows.json`。
- **只有声音的关系**：苏清月随口说的话，要能在她不在的时候被现实一条条应验。埋的时候不要强调。
- **底细分三步揭**：先让读者知道，再让主角猜到，最后当面说破，中间各隔几十章。

**章标题**
- 可以用俗语、成语、旧词配本章的具体人物，制造错位（不引现实典籍，见 `bible.md` 2.4）。不必每章都这样，平实的标题照样可以用。

**结尾**
- 章节停在动作、对白或一个画面上。
- 不写感悟，不写“命运从此改变”式的预告，不总结。

**套话限制**
- “不是 X，是 Y”每章最多 2 次。
- 少用：倒吸一口凉气、脸色一阵青一阵白、陷入了短暂的沉默、翻了个白眼、这就对了。
- 不要大段堆单字成句（例如“风。火。水。响。”）。

## 写完自检

1. **查套话**：
   ```bash
   grep -nE "狠狠干|倒吸一口凉气|一阵青一阵白|短暂的沉默|翻了个白眼" chapters/chapNN.md
   ```
   查出来的改掉；“不是……是……”自己数一遍。
2. **跑守卫**：
   ```bash
   node studio/scripts/cli.mjs guard N
   ```
   会查配角出圈、古今地名混用、人物提前登场、伏笔逾期、时间倒流、套话、“不是……是……”的次数、停顿节拍和场景数。停顿节拍超了，先删掉没有含义的那几处；如果每一处都有用（比如第 23 章那种靠停顿推理的章），再标为确认无误。逐条看：真有问题就改正文；确认是误报（比如史书引文里提到古人、子时对话里提到另一边的人），用 `node studio/scripts/cli.mjs ignore <key>` 标为确认无误（key 是每条末尾〔〕里的内容），并告诉用户标了哪几条。
3. **查设定**：
   - 落星亭：只在子时、只传声、离亭即断。
   - 境界与 `story/characters.json`、地点与 `story/locations.json`、规则与 `bible.md` 一致。
4. **查人物**：苏清月给出帮助时，有没有写出她的局限或误判？林凡是不是又太顺了？
5. **查结尾**：最后一段有没有感悟或总结？
6. **查厚度**：删掉对白之后，还剩不剩一个具体的场面？
7. **查段落**：叙述里连着三段以上的一句话段落，并起来。
8. **查伏笔**：本章新加的暗示，是读者已经知道的吗？是的话删掉，或者换成一个能计量的变化。

## 写完同步

直接改 JSON（两空格缩进，保持原有字段顺序）。星图书房开着时会自动同步。

- **`progress.md`**：更新“进度”，已写章节加一行。
- **`story/chapters.json`**：本章 `status` 改为 `"done"`，填 `recap`（和 progress.md 那一行一致）、`days`、`dayStart`、`dayEnd`。
- **`story/characters.json`**：人物状态有变化（境界、伤势、处境、知道的秘密、称呼……）就给那个人加一条 `{ "chapter": N, "key": "…", "value": "…" }`，同一个 key 的新值会盖住旧值。本章原有带“（计划）”的条目，按正文实际写的改掉或删掉。
- **`story/relations.json`**：关系进入新阶段时，在 `progressions` 里加 `{ "chapter": N, "label": "…" }`。
- **`story/foreshadows.json`**：新埋的伏笔加一条（`planted`、`payoff`、`payoffChapters`，远期留空数组）；收了的改 `"status": "resolved"` 并填 `resolvedIn`。
- **`story/events.json`**：发生历史改动时加一条 `kind: "change"`，写清 `before` / `after` 和 `chapter`。
- **出现新的有名字的人物或地点**：加进 `story/characters.json` / `story/locations.json`（别名写进 `aliases`，古今对照用 `counterpartId` 互相指向并共用坐标）。新的世界观、规则、名词才写进 `bible.md`。
- **正文偏离了大纲**：改 `outline.md` 对应章节和 `story/chapters.json` 的 `plan`，并告诉用户改了什么。

## 改大纲或设定

- **改大纲**：近的章节写到章级（标题 + 一两句内容），远的只写阶段目标。
- **改设定**：世界观和规则只改 `bible.md`；人物、地点、伏笔只改 `story/`。不要在大纲、进度或本文件里另写一份。
- **改了 `bible.md` 的小节标题**：星图书房的设定条目按标题引用 `bible.md`，改完跑一遍 `node studio/scripts/cli.mjs guard`，有“设定引用失效”就去 `story/codex.json` 把 `source.heading` 改成新标题。
- **大改**（新机制、新的主要人物、改结局方向）：先跟用户确认，再动文件。
